1. はじめに

TinyCC（TCC）は、小さく非常に高速な C コンパイラです。外部のアセンブラやリンカに依存せず、 TCC 自身がコンパイル、アセンブル、リンクを行えるよう設計されています。

TCC は ANSI C に加え、ISO C99 の多くの機能と GNU C 拡張（インラインアセンブリを含む）を サポートします。また、コンパイル速度を利用して C ソースをスクリプトのように直接実行できます。

libtcc を使うと、TCC を動的コード生成用バックエンドとして組み込めます。 -b を指定すると、ポインタや配列への境界検査コードを追加できます。

tpp / TCC DX での重要な追加: 本 fork には C++98 を中心とする限定的な C++ サブセットと、一部の追加機能 （例: thread_local）が実装されています。これは完全な ISO C++ コンパイラではありません。 詳細は第9章を参照してください。

元の 0.9.28rc 文書には対象 CPU に関する古い記述があります。この改訂案ではその文面を 歴史的説明として扱い、現在の実装対象は最終的にソース・ビルド構成で確認する方針とします。

2. コマンドラインからの利用

2.1 クイックスタート

usage: tcc [options] [infile1 infile2 ...] [-run infile args ...]

TCC のオプション体系は GCC に近いものです。大きな違いの一つは、 生成したプログラムをファイルへ保存せず、その場で実行して実行時引数を渡せることです。

例意味
tcc -run a.ca.c をコンパイルして直接実行します。
tcc -run a.c arg1a.c を直接実行し、arg1 を main() の第1引数として渡します。
tcc a.c -run b.c arg1a.c と b.c をまとめてコンパイル・リンクして実行します。
tcc -o myprog a.c b.c2つの C ソースをコンパイル・リンクして実行ファイル myprog を生成します。
tcc -o myprog a.o b.oオブジェクトファイルをリンクして実行ファイルを生成します。
tcc -c a.ca.c をコンパイルし、オブジェクトファイル a.o を生成します。
tcc -c asmfile.SC プリプロセッサを通した後にアセンブルし、asmfile.o を生成します。
tcc -c asmfile.sプリプロセスせずにアセンブルします。
tcc -r -o ab.o a.c b.c複数入力をまとめた再配置可能オブジェクト ab.o を生成します。

C スクリプト

Unix 系では、ソース先頭に次のような shebang を置くことで C ソースをスクリプトのように実行できます。

#!/usr/local/bin/tcc -run
#include <stdio.h>

int main(void)
{
    printf("Hello World\n");
    return 0;
}

入力ファイル名の代わりに - を指定すると標準入力から C ソースを読み込めます。

echo 'main(){puts("hello");}' | tcc -run -

3. C 言語サポート

3.1 ANSI C

元文書では、構造体 bit-field と浮動小数点型 （long double、double、float）を含む ANSI C を実装していると説明されています。

3.2 ISO C99 拡張

ISO C99 の多くの機能を実装しています。元文書では complex / imaginary number は未実装とされています。

  • 可変長配列（VLA）
  • 64 bit long long
  • _Bool
  • 現在の関数名を表す __func__
  • __VA_ARGS__ を使う可変引数マクロ
  • ブロック内の任意位置での宣言
  • designated initializer
  • compound literal
  • 16進浮動小数点定数
#define dprintf(level, __VA_ARGS__) printf(__VA_ARGS__)

struct { int x, y; } st[10] = { [0].x = 1, [0].y = 2 };
int tab[10] = { 1, 2, [5] = 5, [9] = 9 };

int *p = (int []){ 1, 2, 3 };
double d = 0x1234p10;

元文書では inline と restrict は無視されると説明されています。 tpp の C++ 経路では inline に C++ 固有の処理が追加されているため、 C++ モードの挙動は第9章の記述を優先してください。

3.3 GNU C 拡張

  • = を省略した古い形式の配列 designator
  • x: value 形式の構造体 field designator
  • \e（ASCII 27）
  • case 1 ... 9: のような case range
  • __attribute__ の一部
  • GNU 形式の可変引数マクロ
  • __FUNCTION__（C99 __func__ として処理）
  • __alignof__
  • typeof(x)
  • computed goto（&&label、goto *expr）
  • GNU 風の inline assembly
  • __builtin_types_compatible_p()、__builtin_constant_p()
  • #pragma pack

元文書が挙げる主な attribute は aligned(n)、packed、section(name)、unused、 cdecl、stdcall、regparm(n)、Windows の dllexport、nodecorate です。

int a __attribute__((aligned(8), section(".mysection")));

int my_add(int a, int b) __attribute__((section(".mycodesection")))
{
    return a + b;
}

3.4 TinyCC 独自拡張

  • __TINYC__ は TCC 使用時に定義されます。
  • 行頭の #! は C スクリプトのため無視されます。
  • 0b101 のような2進整数リテラルを使えます。

4. TinyCC アセンブラ

TinyCC は内蔵アセンブラを持ちます。元文書では gas（GNU assembler）に似た構文を採用し、 C コンパイラ本体は内蔵アセンブラへ依存しないため、より小さい TCC を作る場合は アセンブラ機能を無効化できると説明されています。

.S は C プリプロセス付きアセンブラ、.s は通常のアセンブラ入力として扱われます。 C ソース中の GNU 形式 asm にも内蔵アセンブラが使われます。

4.1 構文

  • 多くの gas 構文をサポートし、token の基本規則は C と同じです。
  • C / C++ 形式のコメントを使用できます。
  • 識別子の規則は C と同じで、元文書では . や $ を識別子に使えないと説明されています。
  • 元文書では整数値は 32 bit までと説明されています。

4.2 式

10進・8進・16進整数、単項 +/-/~、 二項 * / %、& | ^、+ - を扱います。 値は絶対値、または label + offset です。

4.3 ラベル

未定義ラベルを除きローカルとして扱います。gas と同様の数字ラベルを複数回定義でき、 b（backward）と f（forward）で参照できます。

1:
    jmp 1b
    jmp 1f

5. TinyCC リンカ

5.1 ELF 出力

TCC は外部リンカを使わず、再配置可能 ELF、ELF 実行ファイル、動的 ELF ライブラリを直接生成できます。

元文書では、動的ライブラリは生成できるものの C コンパイラが PIC を生成しないため、 生成コードを複数プロセス間で十分共有できないと説明されています。

ライブラリ中の未参照コードを除外します。object/library の走査は1パスで、 GNU ld と同様に入力順が重要です。元文書では --start-group/--end-group は未対応です。

5.2 ELF ローダ

ELF object、archive（.a）、dynamic library（.so）をロードできます。

5.3 Windows PE

Windows 版 TCC は PE 形式の EXE（console / GUI）および DLL を生成できます。 元文書の章名は「PE-i386」ですが、tpp の C++/TLS 拡張は x86_64 Windows で検証されているため、 この表題を現行ターゲット全般の保証とは解釈しないでください。

5.4 GNU linker script

Linux の一部 libc.so などが GNU ld script になっていることに対応するため、 TCC リンカは GNU ld script の一部を読めます。 元文書では GROUP と FILE をサポートし、 OUTPUT_FORMAT と TARGET は無視すると説明されています。

6. メモリ・境界検査

-b で有効にします。元文書では次のような問題を検出対象の例として挙げています。

  • 標準文字列/メモリ関数へ不正な範囲を渡す
  • グローバル・ローカル配列の範囲外アクセス
  • malloc した領域の範囲外アクセス
  • 解放済みメモリへのアクセス
  • 二重 free
{
    char tab[10];
    memset(tab, 0, 11);
}

{
    int *tab = malloc(20 * sizeof(int));
    free(tab);
    free(tab);
}

有効時は __TCC_BCHECK__ が定義されます。

環境変数役割
TCC_BOUNDS_WARN_POINTER_ADD不正な pointer addition を警告します。
TCC_BOUNDS_PRINT_CALLS境界検査呼び出しを表示します。
TCC_BOUNDS_PRINT_HEAP終了時に未解放 heap object を表示します。
TCC_BOUNDS_PRINT_STATISTIC終了時に統計を表示します。
TCC_BOUNDS_NEVER_FATAL境界検査エラー後も可能なら継続を試みます。

__bounds_checking(x) を使ってコードの一部だけ検査を OFF/ON できます。

#ifdef __TCC_BCHECK__
extern void __bounds_checking (int x);
# define BOUNDS_CHECKING_OFF __bounds_checking(1)
# define BOUNDS_CHECKING_ON  __bounds_checking(-1)
#else
# define BOUNDS_CHECKING_OFF
# define BOUNDS_CHECKING_ON
#endif

元文書の注意事項では、対応ターゲット、生成コードの増大、shared library との組み合わせ、 signal handler / multi-threaded fork() と内部 lock の関係などが説明されています。 ターゲット一覧は歴史的に更新されているため、現行の対応範囲はソースで再確認してください。

7. libtcc ライブラリ

libtcc を使うと、TCC を動的コード生成のバックエンドとしてアプリケーションへ組み込めます。

基本的な考え方は、コンパイルしたいプログラムを文字列として libtcc に渡し、 定義されたグローバルシンボル（関数や変数）へホスト側からアクセスすることです。 API の一覧は libtcc.h、最小例は libtcc_test.c を参照します。

tpp / TCC DX では追加検証が必要: C++ global/static object、thread_local、tcc_run()、 direct relocate 後にホストが手動で main() を呼ぶ経路では、 C だけの元文書よりライフサイクル契約が増えています。第9章の実行形態表を参照してください。

8. 開発者向けガイド

この章は TCC 内部を変更する開発者向けです。利用するだけなら読み飛ばせます。

8.1 ファイル読み込み

BufferedFile が、現在行番号を含むファイル読み込み状態を保持します。 元文書では tcc_open() がファイルを開き、tcc_close() が閉じ、 inp() が次の文字を返すと説明されています。

8.2 字句解析

next() は現在ファイルから次 token を読み、next_nomacro() は macro 展開を行わず token を読みます。tok は現在 token、 tokc は数値・文字列などの追加情報を保持します。

tpp では C/C++ 共存のため、C++ 専用 keyword を C モードでは通常の識別子へ戻す処理が追加されています。 この追加は元の開発者ガイドにはありません。

8.3 パーサ

パーサは yacc 等を使わず手書きです。基本的に1パスで動作します。 元文書が例外として挙げるのは、サイズ未確定の初期化配列の要素数計数と、 引数評価順を反転する必要があるアーキテクチャでの事前処理です。

8.4 型

元 TCC は型情報を主に1つの整数へ符号化します。元文書の代表的な基本型値:

配列は VT_PTR と VT_ARRAY の組み合わせとして扱われ、 VLA は別 flag を使います。storage class も解析中は同じ型整数の flag 群として保持されます。

tpp では参照、member pointer、C++ TLS など C++ 用の型/記憶クラス flag が追加されています。 正確な現在値は tcc.h を authority としてください。

8.5 シンボル

symbol は hash 化された symbol stack に保存され、各要素は Sym です。 Sym.v は名前 token、Sym.t は型、Sym.r は主に register、 Sym.c は address・array 要素数・VLA runtime size 位置などに使われます。

主な stack は macro 用 define_stack、global 用 global_stack、 local 用 local_stack、label 用の stack 群です。 sym_find(v) は local を上から検索し、その後 global を検索します。

8.6 セクション

生成コードとデータは Section に書き込まれます。 代表例は text_section、data_section、bss_section、 bound check 用 section、debug 用 stab section、symbol/string table です。

8.7 コード生成

8.7.1 概要

TCC の code generator は、一般的なコンパイラのようなテキストアセンブリを中間出力せず、 リンク可能な binary code を直接生成します。元文書では register based で、 最適化は主に expression level、式の中間状態は value stack に保持すると説明されています。

8.7.2 value stack

式の値は vstack に積まれ、top は vtop です。 各要素は SValue で、型と値の所在を保持します。

#define VT_CONST      0x00f0
#define VT_LLOCAL     0x00f1
#define VT_LOCAL      0x00f2
#define VT_CMP        0x00f3
#define VT_JMP        0x00f4
#define VT_JMPI       0x00f5
#define VT_LVAL       0x0100
#define VT_SYM        0x0200
#define VT_MUSTCAST   0x0400
#define VT_MUSTBOUND  0x0800
#define VT_BOUNDED    0x8000

VT_LVAL は代入可能な左辺値であることを表す重要な flag です。 VT_CMP、VT_JMP/VT_JMPI では、 CPU flags や条件 jump の状態を遅延評価的に保持します。

8.7.3 value stack の操作

vsetc()/vset() が値を積み、vpop() が取り出します。 gv(rc) は vtop を指定 register class へ評価するコードを生成し、 元文書では code generator の最重要関数と説明されています。 gv2() は top 2 要素を対象にします。

8.7.4 CPU 依存 codegen

元文書では i386-gen.c を例として、 load()、store()、gfunc_start()、 gfunc_param()、gfunc_call()、 gfunc_prolog()/gfunc_epilog()、 整数/浮動小数点演算生成と各種型変換関数を挙げています。

8.8 最適化

元文書では定数伝播、乗除算の shift 化、processor flags を保持する比較最適化、 &&/||/! の jump target を使った最適化を説明しています。 より大規模な jump optimization は、より抽象的な中間表現が必要になるため行っていないとされています。

14. 名前解決

14.1 スコープ修飾 ::

できること

  • 先頭の :: によるグローバルスコープ指定（型位置 typedef ::C D;、式位置 ::gfn() / ::gv）。ローカル変数が同名を隠していてもグローバルを選ぶ。
  • クラス内 typedef（typedef unsigned int size_type;）と、その修飾参照 Class::size_type。
  • 二重修飾のクラス外定義 Outer::Inner::method()。
  • 三項演算子との隣接 a ? b : ::c。

14.2 名前の隠蔽

できること

  • 引数やローカル変数がクラス名と同じでも、その変数を優先する（C++ の規則どおり）。
  • 内側の typedef が外側の同名クラスを隠す。
  • メンバ関数内では、自クラスのメンバが同名のグローバル関数より優先される。
  • クラス本体内の型名は、ブロックローカル → 自クラスと直接基底 → 外側クラス → グローバルの順に探す。

実装箇所

  • tccgen.c:2886 cpp_lookup_type_name() — C++ の規則に従った型名の探索（共通ヘルパー）
  • tccgen.c:2987 cpp_tok_starts_type_name() — 文頭の識別子が型名かどうかの判定
  • tccgen.c:2968 cpp_unqualified_class_type_find() — 非修飾のクラス型の探索

amateras での用途

  • base_inc/vec_quat.h:406 struct tex（C++ のときだけ struct tex、C では typedef struct tex）と、inc/UTF_8/cross.h の mmd_gl_free_texture() の引数 tex — 引数がクラス名を隠す形。この処理が無いと tex->gl_tex_id = 0; がコンパイルできなかった（amateras対応作業履歴.md §2.2、回帰テスト dev/test/a9/bug20_shadow_param.cpp）。
  • win_txt::clear() と window_t::clear[4] — 別クラスのメンバ関数名と自クラスのメンバ変数名が同じ形（amateras対応作業履歴.md §2.6、回帰テスト dev/test/a9/bug21_member_vs_global.cpp）。

サンプル

// name_hiding.cpp
struct tex { float u, v; };          // クラス名 tex
struct T { unsigned int id; };

static void free_tex(T* tex)          // 引数名 tex がクラス名 tex を隠す
{
    tex->id = 0;                      // 型名ではなく引数として扱われる
}

int main()
{
    T t;
    t.id = 1;
    free_tex(&t);
    return t.id;                      // 0
}

制限

  • 同じグローバルスコープで struct tex {...}; int tex; の順に書くと再定義エラーになる（逆順や関数内なら可）。
  • グローバル変数の名前を、どこかのクラスのメンバ関数名と同じにはできない。
