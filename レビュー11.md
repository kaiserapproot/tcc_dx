#### 1. `unget` の順序ミスによるトークン再生成の失敗（Phase 4）

**場所**: 差分内の「## 10.6 Phase 4: ctor 呼び出しを emit（1 引数）」セクション **問題点**: 記述されている擬似コードでは、現在のトークンが `(` の状態で以下の処理を行っています。

```
/* tok == `(` の状態で 3 連続 unget */
unget_tok(ctor_tok_v);  /* 1) tok='(' を保存、tok=ctor_tok */
unget_tok('.');         /* 2) tok=ctor_tok を保存、tok='.' */
unget_tok(saved_var_tok); /* 3) tok='.' を保存、tok=var_tok */
```

ここで重大な論理矛盾があります。

1. 現在のトークン `tok` は `(` です。
2. `unget_tok(ctor_tok_v)` を呼び出した瞬間、内部バッファに `(` が保存され、現在の `tok` は `ctor_tok_v` に更新されます。
3. 次に `unget_tok('.')` を呼び出します。この関数の実装（通常は `unget` は現在の `tok` を保存し、指定されたトークンを `tok` に戻す）がどうあれ、\*\*「現在の `tok` が `ctor_tok_v` の状態から `.` を unget する」\*\*という操作自体が意味を成しません。
   * もし `unget_tok(x)` が「x をバッファに積む」という意味なら、2 番目の命令で `.` をバッファに積みますが、その直前の `tok` は `ctor_tok_v` です。
   * もし `unget_tok(x)` が「x を現在の `tok` に戻す（現在の `tok` を保存）」という意味なら、2 番目の命令は「`.` を現在の `tok` に戻す」ことを意図しているようですが、その直前の状態（`tok` が `ctor_tok_v` の時）に `.` が存在しないため、この擬似コードは**現在の** **`tok`** **(`(`) を無視して** **`.`** **を直接 unget しようとしており、論理的に破綻しています**。

**正解の挙動**: トークン列を `var_tok . ctor_tok ( args )` に戻すためには、現在の `tok` (`(`) を保存した上で、逆順に `ctor_tok`, `.`, `var_tok` を unget する必要があります。 しかし、上記のコードは `unget_tok('.')` の時点で、直前の `unget` で `tok` が `ctor_tok_v` に戻されているため、\*\*「現在の `tok` (`ctor_tok_v`) を保存し、`.` を `tok` に戻す」\*\*という動作になります。 結果として、再生成されるトークン列は以下のようになります（`(` が抜けている、または順序が崩れる）。

* **想定**: `var_tok`, `.`, `ctor_tok`, `(`, ...
* **実際の疑似コードの挙動**:
  1. `unget(ctor_tok)`: バッファに `(` 保存。`tok` -> `ctor_tok`
  2. `unget('.')`: バッファに `ctor_tok` 保存。`tok` -> `.` (※ここで `(` がバッファに残っているが、`tok` は `.` になる)
  3. `unget(var_tok)`: バッファに `.` 保存。`tok` -> `var_tok`
  4. `next()` 実行: バッファから `.` を取り出す → **エラー**（期待されるのは `.` の次に `ctor_tok` だが、バッファの順序が逆になる、あるいは `(` が失われる）。

この擬似コードは、`unget` の LIFO (Last In First Out) 性質と現在の `tok` の管理状態を正しく理解しておらず、実装すると**トークン列が** **`var_tok . ctor_tok ( ...`** **ではなく、順序が崩れたもの、または** **`(`** **が失われたもの**として再生成され、コンパイルエラーや予期せぬ動作を招きます。

#### 2. `skip(';')` と `break` の位置によるループ制御の欠陥（Phase 3）

**場所**: 差分内の「## 10.5 Phase 3: 変数領域確保（ctor 呼び出しは skip）」セクション **問題点**:

```
if (tok == ',') { next(); continue; }
skip(';');
break;
```

このコードは、宣言文の末尾処理を `decl()` のループ内で行おうとしています。

* `Foo f(5);` の場合、`(` をスキップし、引数リストをスキップした後、`tok` は `;` になります。
* `skip(';')` で `;` を消費し、その後 `break` でループを終了します。これは正しい動作に見えます。

**しかし**、以下のケースで問題が発生します。

* **複数宣言**: `Foo f(1), g(2);`
  * `f(1)` の処理で `tok` が `,` になった場合、`continue` でループを繰り返します。
  * 次の反復で `g(2)` を処理し、その後 `;` に到達して `break` します。
  * **問題**: `decl()` の通常パス（関数宣言や通常のメンバ宣言など）では、カンマ区切りの宣言は `type_decl` 内で処理されることが多いですが、この擬似コードは\*\*「クラス型の変数宣言のみで、かつ引数付きの ctor 呼び出し形式」\*\*を特定して特殊処理しています。
  * もし `decl()` のループが、通常の変数宣言（`Foo f;`）も同じループ内を回すのであれば、`Foo f;` の場合、`tok` は `;` です。`if (tok == ',')` は偽、`skip(';')` で `;` を消費し、`break` します。
  * **致命的な欠陥**: `break` によりループを即座に終了させています。もし `decl()` のループ内で、この宣言の後に**さらに別の宣言**（例：`Foo f(1); int x = 0;`）が続いている場合、`int x = 0;` のパースがスキップされ、**宣言が欠落するバグ**になります。
  * 正しい実装では、`skip(';')` 後に `continue` し、ループを継続すべきです（または `decl()` の構造上、この `break` が意図された場所か確認が必要ですが、擬似コードの文脈では「宣言処理完了＝ループ終了」と解釈すると、複数宣言のサポートが壊れます）。

#### 3. `cpp_find_ctor_field` の実装ロジックの誤り（Phase 1）

**場所**: 差分内の「## 10.3 Phase 1: ヘルパー追加」セクション **問題点**:

```
if ((f->v & ~SYM_FIELD) != class_name_tok)
    continue;
```

この条件式は、`f->v` から `SYM_FIELD` を除いた値が、クラス名のトークン番号と一致するか確認しています。

* **問題**: `find_field` やメンバ検索の一般的な実装では、フィールド名（トークン）を比較する際、`SYM_FIELD` マスクを適用するのは正しいですが、**`class_name_tok`** **の取得方法**に依存します。
* 擬似コードでは `class_name_tok = class_sym->v & ~SYM_STRUCT;` と定義されています。これは「構造体シンボル自体のトークン番号」を取得しています。
* しかし、C++ のクラス構文において、クラス名とコンストラクタ名の関係は、必ずしもシンボルの `v` フィールドが直接一致するとは限りません（特にマングリングや内部表現によっては異なる場合があります）。
* さらに、この条件式 `(f->v & ~SYM_FIELD) != class_name_tok` は、\*\*「フィールドのトークン番号がクラス名と一致するか」\*\*を判定しようとしていますが、`class_sym->v` が本当に「クラス名のトークン番号」を保持している保証が差分からは得られません。
* もし `class_sym->v` がシンボルテーブル上のインデックスや他のメタデータであれば、この比較は常に失敗し、コンストラクタフィールドが見つからず、FEAT-4B の機能が完全に機能しなくなります。
